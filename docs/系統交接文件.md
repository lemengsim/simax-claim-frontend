## 一、系統概覽

### 目的

SIMAX 品牌在 MOMO 電商平台販售 eSIM 商品。顧客下單後，系統全自動向 eSIM 廠商（DJB / 世界移動）叫貨取得 QR Code，顧客再透過 SIMAX 自助領取網站取得 eSIM。

### 目前上線渠道

| 渠道 | 進件方式 | 狀態 |
|------|----------|------|
| MOMO | 每5分鐘 SCM API 撈單 | ✅ 上線 |
| 蝦皮 | Gmail 解析付款確認信 | ❌ 未建立 |
| 官網 | Gmail 解析付款確認信 | ❌ 未建立 |

> **注意**：Google Sheets「自助領取紀錄」C欄出現「官網」= MOMO 顧客透過網站前台自助領取，不是官網獨立渠道。

## 二、系統架構圖

```
顧客在 MOMO 下單
        ↓
[GCP VM simax-engine] — 每5分鐘
  momo-ingest.js
    1. 打 MOMO SCM API (unsendCompanyQuery)
    2. AES-128-ECB 解密 dataList
    3. core-mapper.js 比對廠商代碼
    4. UPSERT → Supabase orders 表 (status: pending)
        ↓
  dispatch-worker.js (由 express-server.js 即時呼叫)
    ├── DJB: POST form → buy → 輪詢取QR → LPA字串
    └── WM:  POST json → mybuyesim → WM直寄Email給顧客

顧客開啟 simax-clone.vercel.app
  Step1a: 輸入MOMO訂單號 + Email
  Step1b: 輸入電子票券序號 (12碼英數字)
  Step2:  確認商品 (多件時顯示列表)
  Step3:  顯示 QR Code + ICCID (已支援)
        ↓
[Vercel: simax-clone]
  /api/verify → GCP /api/internal/verify
  /api/claim  → GCP /api/internal/redeem
        ↓
[GCP express-server.js port 3001]
  1. internalKey 驗證
  2. 查 Supabase 防重複領取
  3. verifyMomoOrder (C1105 確認已出貨)
  4. mapProductToVendor 比對廠商
  5. dispatchOrder 叫貨取 QR
  6. UPSERT Supabase (status: ready_to_claim)
  7. appendToSheetLog 寫 Google Sheets
  8. 回傳 items[] 給前台
```

## 四、廠商串接說明

### DJB（第一廠商，主力）

- API 格式：`application/x-www-form-urlencoded`
- 流程：下單 `/api/order/buy` → 輪詢 `/api/order/info`（最多5次，每次3秒）
- 認證：`key` + MD5 Checksum（Base64(IV + YYYYMMDD + source_number)）
- QR 格式：`LPA:1$rsp.esimcase.com$...`（前台判斷 startsWith('LPA:')）
- PENDING 狀態：輪詢15秒未取得時回傳 `DJB_PENDING:<djbOrderId>`，前台顯示「準備中」

### WM / 世界移動（第二廠商）

- API 格式：`application/json`
- 流程：單次下單 `/Api/SOrder/mybuyesim`，WM 直接寄兌換碼 Email 給顧客
- 認證：SHA1( merchantId + deptId + email + prodListStr + token )
- QR 格式：`WM_ORDER:<wmOrderId>`（前台判斷 startsWith('WM_ORDER:')，顯示「已寄送」）
- 無需輪詢，WM 自行處理寄送

## 六、Supabase orders 表 Schema

```sql
order_id        TEXT PRIMARY KEY  -- MOMO訂單號（多件共用基號）
platform        TEXT              -- 'MOMO' | '蝦皮' | '官網'

retry_count     INTEGER

created_at      TIMESTAMPTZ
```

## 七、已知待辦事項

### 功能待建立

| 項目 | 優先度 | 說明 |

### 已知地雷 ⚠️

- **VM 與本地程式碼不同步**：本地 express-server.js 是簡化版，VM 上有 ticketPins 處理邏輯。修改 VM 時務必用 `awk`/`sed` 確認現有程式碼再 patch，不可直接覆蓋
- **Plans 分頁需公開**：core-mapper.js 用公開 CSV URL 讀取字典，若 Sheet 改為私有則字典無法載入
- **多件訂單 qr_code_data 格式**：單件存字串，多件存 JSON 陣列字串，前台 normalizeResponse 需能處理兩種格式
- **DJB QR 輪詢**：只輪詢 5 次（15秒），超時回傳 PENDING，顧客需重新領取；activation-poller 預計補回這段
- **git index.lock**：沙箱無法刪除 Windows mount 的 lock 檔，每次 push 前需在 PowerShell 執行 `Remove-Item`

## 八、重要決策記錄

| 決策 | 原因 | 排除的方案 |
|------|------|-----------|
| VM 即時叫貨（不用排程批量） | 顧客領取時需即時拿到 QR Code | 批量排程叫貨（顧客等待時間長）|
| 電子票券序號驗證 (ticketPin) | MOMO 要求，防止未持有票券的人領取 | 僅用訂單號+Email 驗證 |
| 廠商優先 DJB，fallback WM | DJB 回傳 LPA 直接安裝，體驗較好 | 隨機選廠商 |
| Plans 分頁用公開 CSV 讀取 | 不需要 OAuth scope，部署簡單 | googleapis + service account |
| Supabase service_role key | 繞過 RLS，後端操作不受前台權限限制 | anon key + RLS policy |
